[1-A] 웹 서버  ── src/web/app.py

 2. 핵심 진입 함수 run_for_web()  [agent_client.py:944]
================================================================================

  async def run_for_web(user_task):
      try:
        1) session, tool_desc = await _ensure_mcp_session()   # MCP 툴 서버 연결
        2) global_plan        = await _call_global_planner(user_task)
        3) ctx_examples, lessons = self._recall_memory(user_task)  # ← 메모리 회상
             • memory.retrieve_similar  : 유사 과거 궤적 top3 → planner 컨텍스트
             • semantic_memory.retrieve_relevant : 관련 교훈 top5
             • best-effort: 임베딩/DB 실패 시 빈값으로 degrade (run은 계속)
        4) result, meta       = await _run_flow(user_task, global_plan, ...,
                                                ctx_examples, lessons)
        5) self.memory.save_trajectory(user_task, meta.plan,    # 에피소드 메모리 저장
                                       result, meta.score, meta.lessons)
             ※ meta는 _build_trajectory_meta(outcome, ...)가 산출 — outcome별
               실제 score(0.5~0.9) + 미해결 비평점을 lessons로 기록 (과거엔
               0.8/[] 하드코딩이라 학습 루프가 죽어 있었음).
        6) return result
      except Exception as e:
        return f"오류: {e}"     # 어떤 단계가 깨져도 사용자에겐 문자열 반환

 5. _run_flow — 멀티 에이전트 오케스트레이션 (심장)  [agent_client.py:760]
================================================================================

 전체 구조: "Tier-1 병렬 수집 → 비평/방어/심판 → per-focus 재실행 루프 → Tier-2 통합 → 요약"

 핵심 모델: per-focus REVISION (과거의 additive 모델에서 전환)
   - findings_by_focus[focus]를 키로 둠. 같은 focus를 다시 실행하면 블록이
     OVERWRITE = 제자리 수정(revision). 다른 focus는 ADD.
   - Reflector가 focus별로 sufficient/부족을 판정:
       • sufficient → 그 focus는 freeze(다시 안 봄)
       • 부족 + Judge가 타당하다고 인정 → 그 focus를 issues 들고 RE-RUN
   - 못 고치면 revision cap(MAX_FOCUS_REVISIONS) 후 freeze + unresolved 기록.

 ───────────────────────────────────────────────────────────────────────────
 5-0. 사전 준비
 ───────────────────────────────────────────────────────────────────────────
   - Semaphore(3): 동시에 도는 subtask를 최대 3개로 제한 (rate-limit 보호)
   - tool_cache: 동일 (tool+args) 호출 결과를 Future로 캐시 → 중복 호출 제거
   - market_facts = _market_consistency_anchor(ticker)  [agent_client.py:314]
       price × shares ≈ market cap, 52주 범위를 yfinance로 직접 계산해
       "검증된 시장 사실"로 만들어 Reflector에 ground truth로 제공.
       (LLM의 stale 사전지식 대신 산술적으로 모순을 잡게 함)
   - deadline = now + FLOW_TIME_BUDGET_SEC(기본 480초)
       웹 600초 하드 타임아웃 전에 멈추고 부분 리포트라도 내보내기 위함.
   - 상태 변수:
       work_items   : [(subtask, critique, prev_findings)] — 이번 라운드 실행분.
                      iter0 = 원본 plan (critique=None). 라운드마다 재구성.
       revision_count[focus] : focus별 재실행 횟수 (cap = MAX_FOCUS_REVISIONS)
       attempting_issues     : 이번 라운드가 해결하려는 비평점(중단 시 unresolved행)

 ───────────────────────────────────────────────────────────────────────────
 5-1. 메인 루프  for global_iter in range(MAX_GLOBAL_ITER=3)
 ───────────────────────────────────────────────────────────────────────────

   ┌─ 진입 가드 (iter ≥ 1) ───────────────────────────────────────────────┐
   │   • deadline 초과 → attempting_issues 기록 후 outcome=deadline, 탈출   │
   │   • work_items 비었음 → outcome=no_new_subtasks, 탈출                  │
   └───────────────────────────────────────────────────────────────────────┘

   ┌─ 실행 ───────────────────────────────────────────────────────────────┐
   │  work_items 를 asyncio.gather 로 병렬 실행:                           │
   │     각 항목 → _run_subtask(subtask, critique=crit,                    │
   │                            previous_findings=prev, ...)  [§6 참조]    │
   │     (iter0은 반드시 완료 / iter≥1은 wait_for로 남은예산 시간박싱)     │
   │                                                                       │
   │  결과를 focus 키로 OVERWRITE:                                         │
   │     findings_by_focus[focus] = r.findings  ← 같은 focus면 제자리 수정 │
   │     valid_by_focus[focus]    = r.valid                                │
   │                                                                       │
   │  all_findings = _assemble_findings()                                  │
   │     - valid 블록은 그대로                                             │
   │     - 비어있/실패 블록은 "⚠️ INCOMPLETE 커버리지 공백"으로 명시       │
   │                                                                       │
   │  critique = await _call_global_reflector(...)  [§5-2]  → last_critique │
   │     approved → outcome=approved_early/late, 탈출                      │
   │     마지막 iter인데 미승인 → outcome=maxed, 비평점 unresolved, 탈출   │
   └───────────────────────────────────────────────────────────────────────┘

 ───────────────────────────────────────────────────────────────────────────
 5-2. 비평 ↔ 방어 ↔ 심판 → 다음 라운드 work_items 구성
 ───────────────────────────────────────────────────────────────────────────
   Reflector가 approved 하지 않았고, 아직 마지막 iter가 아니면:

     0) Reflector 출력에 subtask_verdicts[{focus, sufficient, issues}] 포함.
        (focus별 충분/부족 + 부족 사유. missing_coverage는 "블록 없는 새 각도"만)

     1) defense = _call_global_planner_defense(critique, all_findings, ...)
          프롬프트: global_planner/defense.md
          ★ 이제 현재 findings + per-subtask verdicts를 함께 받음 (과거엔 critique
            텍스트만 봐서 이미 모은 걸 또 제안하던 버그 — 수정됨).
          출력 분기:
            revise[]       : 기존 focus 재실행 (제자리 수정, 같은 focus명)
            new_subtasks[] : 완전히 새 focus (새 각도)
            concede[] / defense : 인정 / 범위 밖 방어

     2) verdict = _call_judge(critic, defense, ...)
          프롬프트: judge/system.md  (독립 심판 — Planner 자가판정 모순 방지)
          verdict == "planner" 또는 revise·new 둘 다 없음
             → outcome=judge_planner, 유효지적 unresolved, 탈출

     3) 다음 라운드 work_items 재구성 (verdict == "reflector"):
          revise 항목마다:
             - revision_count[focus] ≥ cap → freeze + 그 issues unresolved행
             - 아니면 revision_count[focus]++, work_item 추가:
                 critique = {weak_points: verdict_by_focus[focus].issues}
                 prev     = 그 focus의 "현재 블록"만 (전역 blob 아님)
             - defense가 존재하지 않는 focus명을 적었으면 new 취급
          new_subtasks 항목: (subtask, 전체 critique, all_findings) 추가
          work_items 비면 → outcome=no_new_subtasks, 탈출

 ───────────────────────────────────────────────────────────────────────────
 5-3. Tier-2 — 통합 밸류에이션 슬롯  [agent_client.py:900]  (단일 종목만)
 ───────────────────────────────────────────────────────────────────────────
   문제: Tier-1 subtask들은 병렬이라 서로의 결과를 못 본다. 그래서
         "뉴스 촉매가 성장가정에 반영" / "저항선이 상단을 제한" 같은
         교차 사실이 밸류에이션에 못 들어감.
   해결: ticker가 있고 subtask가 1개일 때, 합성 비평(synth_critique)을 만들어
         _run_subtask를 딱 한 번 더 실행. Tier-1 findings를 previous_findings로
         넘겨서 planner가 예: stock_dcf를 growth_override로 재실행하도록 유도.
   - deadline 안에서만, 실패/초과 시 Tier-1 리포트 그대로 출고.

 ───────────────────────────────────────────────────────────────────────────
 5-4. 최종 요약  [_call_summarizer: agent_client.py:647]
 ───────────────────────────────────────────────────────────────────────────
   - 프롬프트: summarizer/system.md (current_date 주입)
   - 입력: 전체 findings + unresolved_points(미해결 공백 목록)
   - 미해결점은 [투자의견]에서 "한계로 명시, 컨빅션 낮춤"하도록 강제.
     (데이터 날조 금지 / 침묵 누락 금지)
   - 반환: 한국어 투자 리포트 문자열 → run_for_web 으로 돌아감.


================================================================================
 6. _run_subtask — 하위 과제 1개 실행 단위  [agent_client.py:718]
================================================================================

  하나의 subtask(focus) 안에서:

   인자: critique / previous_findings (revise면 그 focus의 자기 블록),
         context_examples / semantic_knowledge (§8 메모리 회상 결과) 가
         _run_flow에서 그대로 스레딩됨.

   1) plan = await _call_planner(task, tool_desc, context_examples,
                                 semantic_knowledge=..., subtask_focus=focus,
                                 critique=..., previous_findings=...)
        프롬프트: planner/system.md (+ subtask_context, critique_context,
                  memory_context, semantic_context 동적 조립)
          • memory_context  ← context_examples (유사 과거 궤적)
          • semantic_context ← semantic_knowledge (관련 교훈)
          • critique_context ← critique + previous_findings
        출력: 실행할 툴 스텝 배열  [{tool, args, reason}, ...]

   2) _execute_plan(plan): 각 step 마다
        result = session.call_tool(tool, args)   # MCP 캐시 경유(_cached_call_tool)
        tool_output = result.content[0].text
        ┌─ 툴별 해석 에이전트 라우팅 ───────────────────────────────────┐
        │  tool == "stock_news"       → _call_news_analyst(output)       │
        │                               (news_analyst/system.md)         │
        │                               + _sentiment_guardrail:          │
        │                                 pos-neg 격차<15pp면 NEUTRAL 강제│
        │  tool == "stock_technical"  → _call_technical_analyst(output)  │
        │                               (technical_analyst/system.md)    │
        │  그 외                       → _call_executor(step, output,     │
        │                                  tips=get_tool_tips(tool))      │
        │                               (executor/system.md + 절차 메모리 │
        │                                팁: 과거 성공 실행 요약 주입)     │
        └────────────────────────────────────────────────────────────────┘
        findings += "### {reason}\n{interpretation}\n"
        (툴 실패 시 "### tool: Failed - {e}" 로 기록 → 나중에 공백으로 surface)

   3) return { focus, findings, valid: _findings_usable(findings) }
        _findings_usable: 실패 헤더가 아니고 본문이 실제로 있는 섹션이
        하나라도 있으면 True (빈 헤더만 있는 경우 False) [agent_client.py:270]

 7. LLM 호출 계층 — Per-Agent Provider Mixing  [_call_llm: agent_client.py:421]
================================================================================

  - 에이전트 역할마다 모델을 다르게 지정 가능 (config.py):
        PLANNER_MODEL / EXECUTOR_MODEL / SUMMARIZER_MODEL /
        NEWS_ANALYST_MODEL / TECHNICAL_ANALYST_MODEL /
        GLOBAL_PLANNER_MODEL / GLOBAL_REFLECTOR_MODEL / JUDGE_MODEL
    미설정 시 LLM_MODEL 로 폴백.
  - _detect_provider(model): 모델명 접두사로 provider 자동 감지
        claude-*  → anthropic
        gemini-*  → gemini
        gpt-/o1-/o3-/o4-* → openai
        그 외     → groq
  - provider별 client는 모듈 로드시 API 키 있는 것만 초기화(_provider_clients).
    LLM_PROVIDER의 client가 없으면 MOCK_MODE=True (MockLLM으로 동작).
  - 신뢰성 장치:
       _rate_limit_gate(provider): provider별 최소 간격(_MIN_WAIT) 강제
       _is_retryable_error + 지수 백오프 재시도 (LLM_MAX_RETRIES=3)
       anthropic 경로는 system 프롬프트에 ephemeral cache_control 적용
  - blocking SDK 호출은 loop.run_in_executor로 감싸 async 유지.

 8. 메모리 시스템  src/memory_store.py + src/database.py (SQLite)
================================================================================

  세 종류의 메모리 (database.py가 SQLite 테이블/커넥션 관리):

  ★ 읽기-쓰기 루프가 실제로 연결돼 있음 (과거엔 write-only로 죽어 있었음):
     쓰기: run_for_web 끝 save_trajectory(meta) — meta는 _build_trajectory_meta가
           outcome별 score(0.5~0.9) + 미해결 비평점 lessons를 산출.
     읽기: run_for_web 시작 _recall_memory() — retrieve_similar + retrieve_relevant를
           planner까지 스레딩(§6). + _execute_plan이 get_tool_tips를 executor에 주입.

  [Episodic]  MemoryStore — 과거 "질문→플랜→결과→점수" 궤적
     • save_trajectory: run_for_web 끝에서 저장.
         임베딩 유사도 ≥ 0.92면 기존 항목과 dedup:
            점수 개선 → 전체 덮어쓰기 + lessons 머지
            동일/악화 → lessons 만 머지
         (score가 outcome별로 실제 달라지므로 이 dedup/overwrite 게이트가 작동)
     • retrieve_similar: 유사 과거 플랜 top3 (cos<0.5는 노이즈로 제외)
         → _recall_memory가 _format_trajectory_examples로 문자열화해 planner의
           memory_context(context_examples)로 주입.

  [Semantic]  SemanticMemory — 일반화된 교훈(lesson)
     • retrieve_relevant: 현재 과제와 유사한 교훈 top5 → planner semantic_context로 주입.
     • compress_period: 주→월→연 롤오버 시 클러스터링 후 LLM으로 1~2개로 압축
         (_cluster_lessons 그리디 코사인 군집 → _merge_with_llm)

  [Procedural]  ProceduralMemory — 툴 실행 이력/팁
     • get_tool_tips: 성공했던 툴 실행 요약을 executor에 힌트로 제공
         (_execute_plan에서 stock_news/stock_technical 외 툴 해석 시 tips=로 전달)

  [임베딩]  _get_embedding (우선순위 폴백):
       openai → gemini(models/gemini-embedding-001) → 로컬 multilingual MiniLM
       모두 실패 시 결정적 RNG 768차원(검색 무의미, 경고 출력)
     • reembed_if_model_changed: 임베딩 모델이 바뀌면 자동 재임베딩 마이그레이션
       (run_for_web 객체 생성 시 호출, agent_client.py:378)

 11. 흐름 종료(outcome) 라벨 정리  — _run_flow가 왜 멈췄는지
================================================================================
   approved_early   iter0에서 Reflector 즉시 승인 (가장 깔끔)   → score 0.9
   approved_late    정제 후 승인                                → score 0.8
   judge_planner    Judge가 "Planner 충분" 판정                 → score 0.75
   no_new_subtasks  더 돌릴 revise/new work_items 없음 (cap 포함) → score 0.6
   maxed            MAX_GLOBAL_ITER 소진했는데도 미승인          → score 0.5
   deadline         시간예산(480s) 초과로 조기 종료             → score 0.6(기본)
   ※ outcome → score/lessons 는 _build_trajectory_meta + _TRAJ_SCORE_BY_OUTCOME가
     실제로 산정해 save_trajectory로 기록 (과거 no_progress 라벨은 per-focus
     revision cap으로 대체되어 제거됨).

 12. 설계 핵심 요약 (왜 이렇게 만들었나)
================================================================================
  • 멀티 에이전트 분업: 계획/실행/해석/비평/심판/요약을 분리 → 각 역할에
    최적 모델을 꽂고(Provider Mixing), 비평-방어-심판으로 자기교정.
  • per-focus revision: Reflector가 focus별로 판정 → 충분하면 freeze, 부족하면
    그 focus를 제자리 재실행(overwrite)해 결함을 고침. 과거 additive 모델은
    기존 부실 블록을 freeze하고 새 블록만 추가해 결함을 못 고쳤음.
  • 환각 방지 3종: ① 티커 상장정보 교차검증 ② market_facts 산술 앵커
    ③ current_date 주입(과거 데이터를 현재로 오독 방지).
  • 무한루프/타임아웃 방지: MAX_FOCUS_REVISIONS(focus별 재실행 상한),
    480s deadline, 시간 박싱된 정제 라운드, MAX_GLOBAL_ITER.
  • 정직한 보고: 무데이터는 "커버리지 공백"으로 표면화, 못 고친 focus 이슈는
    unresolved_points로 요약에 한계 명시 (날조·침묵 누락 금지).
  • MCP 싱글톤 + tool_cache: subprocess/툴호출 비용 최소화.
  • 메모리 3계층(읽기-쓰기 루프 연결): 궤적(episodic)/교훈(semantic, 압축롤오버)/
    툴팁(procedural) — 회상은 planner·executor에 주입, 결과는 outcome별 score+
    lessons로 저장돼 다음 질문에 다시 반영됨.

  ⚠️ README 와의 차이(현 코드 기준): FinBERT 감성분석·ML 가격예측·별도
     Intent Extractor 단계는 제거됨. 현재는 Global Planner가 직접 질문을
     파싱하고, 감성은 stock_news + news_analyst(+sentiment_guardrail)로 처리.
